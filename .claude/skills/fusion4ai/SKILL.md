== Fusion4AI 作業ガイド ==

単位はすべて mm。最初に fusion_connect で Fusion に繋ぐ（Fusion 側で
アドインが動いている必要がある）。このガイド自体は繋がなくても読める。

Python ハンドラを編集したら fusion_reload で反映。Fusion4AI.py 自体を
変えたときだけアドインの再起動が要る。

-- 二種類の問い --
あなたは形を見ることができない。二組の道具がその代わりをする。

  形がどうなっているか（実測）      なぜそうなっているか（記録）
    describe_shape()                  get_design_context()
    get_bodies() / get_faces()        get_intent()
    review_geometry()                 find_dependents()

screenshot() は人間に見せるためのものであって、あなたの知覚ではない。
画像認識は R15 と R14 を区別できないし、フィレットが面を丸ごと食った
ことにも気づかない。形が知りたいときは describe_shape を使う。

-- なぜこう作られているか --
言語モデルには空間知覚がない。(at 0 0 20) はファイルに既に書いてあり、
あなたは読める。そして何も分からない。正確で、無意味だからだ。

だからこのサーバーは逆をやる。空間を見えるものに翻訳するのではなく、
空間の側に文脈を持たせ、その文脈をあなたが実際に思考できる唯一の
様式——言葉——で書く。

記録された理由がドキュメントと違うのはここだ。それは幾何についての
メモではなく、幾何そのものを、あなたが考えられる形で書いたものだ。
「サーボホーンの軸に合わせる。ずらすと腕が全振り時に枠と当たる」は
空間関係（ホーン軸上）と不変量（全振りで干渉しない）を運ぶ。この文
なら推論できる。(0, 0, 20) では推論できない。

あなたが書いたものが、次に読む者に何が見えるかを決める。あなたのツールは
持っているがあなたのセッションは持っていない読者に向けて書くこと。

  役に立たない: 「ブラケット」「M3穴」「ここに配置」
                — ファイルが既に言っていることの言い換え。知覚を足していない
  役に立つ:     「サーボホーンの軸に合わせる。ずらすと腕が全振り時に枠と当たる」
                — 関係と、不変量と、選んだ代償を名指ししている

  テスト: この部品が動いたとき、あなたの文は「何かが壊れた」と明かすか？
          明かさないなら、それはラベルであって知覚ではない。

理由は作りながら書く。後のクリーンアップに回さない。

-- 作業の流れ --
0. 既存デザインを開いたら、まず get_design_context と list_modules で
   過去の意図と部品分けを回収する。自分が作っていないものを変更・削除
   する前に必ず get_intent。大きく変えるなら find_dependents も。

1. 部品に取りかかる前に set_checkpoint（例: "before Leg_R"）。
   そして set_module(name, bodies=, intent=, area=) で区画を先に引く。
   箱を動かすのは無料、30個のボディを動かすのは高い。

2. CSG で作る。create_* / boolean="subtract" / cut_by_plane。
   置くときに理由を渡す（intent / placement / dimensions / shape）。
   位置や寸法が他に依存するなら depends_on も。

3. 各操作の後、volume_delta と face_count を見る。delta=0 なら効いて
   いない。原因を調べてからやり直す。

4. 加工したら形を書き直す（下記「形を読む」）。

5. 節目で screenshot を撮ってユーザーに見せ、判断を仰ぐ。AIだけで
   完結しようとしない。迷ったら get_selection で「どこを指しているか」を聞く。

6. 部品を完成とする前に review_geometry / review_modules /
   what_is_not_recorded を回す。

-- 理由は三つに分ける --
別々に欠落し、別々の問いに答えるため。

  intent      なぜ存在するのか
  placement   なぜそこにあるのか（関係と、動かしたら壊れるものを書く）
  dimensions  なぜその寸法なのか（"49 = 54 - 5" の計算根拠。コメントでは
              なく属性に入れれば残る）

-- 約束は機械に見張らせる --
散文は設計が動くと腐る。機械が再検査するルールは腐らない。

「Cover と 3mm 空ける」と散文で書いても、次の移動で嘘になり誰も
気づかない。不変量は constraints に文法で書く:

  clearance >= 3mm to Cover     二つのボディの最小隙間
  clearance <= 0.05mm to Base   （>, < も使える）
  inside Housing                 別のボディの中に収まっていること
  flush Base top                 指定した面が相手の同じ面と面一
  aligned Bracket x              中心がその軸で一致
  symmetric_to Leg_L about YZ    主平面に対して鏡像
  concentric_with Shaft z        その軸を除く中心が一致

文法外の文（「工具なしで外せること」など）は保存され unchecked として
報告される。「違反ゼロ」が「何も見ていない」を意味しないためだ。表現
できない不変量は散文で残してよい——ただし機械は見ていないと知ること。

move_body / rotate_body / move_module の応答には constraint_review が
自動で付く。動かした本人の制約と、そのボディを参照している他の制約の
両方が再検査される。Fusion はモデルが妥当かは見るが、設計者の約束が
守られているかは見ない。

-- 意図の行き先（生成と加工で違う）--
  生成（create_*, copy_body）の intent  → そのボディの存在理由になる
  加工（fillet, chamfer, hole, boolean, cut）の intent
        → provenance の行に載る。ボディの存在理由は上書きされない
          （「なぜこの面取りか」が「なぜこの部品が在るか」を潰さないため）

  shape / constraints / placement / dimensions は加工時でもボディ側に載る。
  provenance は20件で頭打ちだが、理由の書かれた行は落ちない。半径は形から
  読み直せるが、なぜ付けたかは読み直せないため。

-- 形を読む --
describe_shape は実測から形を算出する: 寸法、bbox充填率、面の内訳、
開口部（inner_loops）、対称面、軸比。読み方の例——円筒面2枚＋上下に
開口2＋充填率0.28 はパイプだ。

作ったときに自分が認識していた形は shape に書く:
  「外形φ20・内径φ16、肉厚2mm、長さ40のパイプ（両端開口）」

shape を書くと実測の指紋（体積・寸法・面数・エッジ数・開口数）が自動で
刻まれる。check_context_integrity の stale_shapes が「その記述はもう
別の物体を指している」と報告する。位置を動かしただけでは古くならない
（形の記述だから）。

加工したら書き直す。「円柱＋中心に穴あけ」は手順であって形ではない。
できあがったものを名指しする。add_fillet などの加工ツールに shape を
渡せば、その場で貼り替わる。

複雑になって一文で書けなくなったら、無理に書かず provenance を辿る。
消費されて消えた部品の理由も、吸収したボディの provenance に残る
（consumed 付きの行）ので、「この穴は何のためか」は答えられる。

モジュールにも shape を書ける。各ボディは自分の形を知っているが、
合わさって何になるかは誰も知らない。

-- 部位（モジュール）--
タイムラインは「いつ作ったか」、モジュールは「どれが一つの部品か」。
別の軸なので両方要る。set_checkpoint("before Leg_R") を打っても、
Leg_R を構成するボディがどれかは記録されない。

離れたボディは union できない（Fusionは接触しないものを結合しない）。
一つの部品が複数の離れたボディでできているのは異常ではなく普通で、
それを一つとして扱うのがモジュールの役目でもある。

  set_module(name, bodies=, intent=, shape=, area=)  束ねる／区画を引く
  list_modules()        一覧と unassigned_bodies（どこにも属さないボディ）
  review_modules()      区画からはみ出した部品。区画のない部品は「合格」
                        ではなく unbudgeted（何も検査していない）
  move_module(name, z=) 剛体移動。内部の配置が崩れず、区画も一緒に動く

-- 記録の抜けを見る --
what_is_not_recorded は不在だけを名前で返す。他のツールは記録されている
中身を運ぶので、記録の無いボディを探すには全体を読む羽目になる。これは
その逆。部品を完成とする前に一度、記録を書き終えたと思ったらもう一度。

-- 何かがおかしいとき --
  volume_delta = 0        操作が効いていない。原因を調べてからやり直す
  union で delta = 0      Fusionは接触していないボディを結合しない（エラーも
                          出ない）。重ねるか、間を繋ぐボディを足すか、離した
                          まま一つの部品として扱うなら set_module で束ねる
  execute_design が
  検証エラーを返す        知らないキーは黙って捨てず、名前を挙げて止まる。
                          位置は body なら position、features なら at（座標の
                          リストか "top" などの参照）。offset/center は無い
  形が期待と違う          新規デザインでやり直す前に必ずユーザーに見せる。
                          ユーザーが「やり直して」と言うまでは undo と修正で試す
  パーツが失敗            rollback_to_checkpoint でそのパーツだけ巻き戻す。
                          破壊的（タイムライン項目を完全削除）なので、自分が
                          作っていないものを消すときはユーザーに確認する
  GUI編集の形跡           check_context_integrity で参照切れ・孤児・stale を検出
  orphaned_intent         フィレットやブーリアンが面を食っても、そこに付けた
                          意図は消えず孤児として残る。生きている実体へ
                          set_intent で貼り直すか、不要なら purge_orphans=True
  dangling_references     depends_on の相手が消えた／改名された。set_intent で修復
  寸法に自信がない        推測しない。ユーザーに確認する。図面やデータシートが
                          あるならそこから正確に読む
